# P6 workspace encryption

The v2 store encrypts events and checkpoints with libsodium.js
XChaCha20-Poly1305-IETF, fresh nonces and purpose-separated keys. It authenticates
the manifest and device directory before replaying the unchanged v1 logical
records. Downgrades observed on this Mac and corrupt complete records fail
closed. The migration/rotation/restore driver uses a new identity and key, keeps
the source and verified backup, and publishes the manifest last. A private
journal records copy and verification phases. An interrupted candidate is never
automatically resumed or activated; choose a new destination after reviewing
the old candidate. The core rebuilds checkpoint caches from retained history.

Settings → Privacy & Data starts the native copy and lock operations. Backup &
Recovery starts native encrypted restore. The Fulcrum app menu supplies unlock
and rotation. The recovery card is displayed/re-entered only in native AppKit
and travels to the core on bounded private pipes. The helper denies callers
outside the valid same-team bundled core and stores non-syncing 32-byte keys in
the data protection Keychain. It never writes plaintext keys to disk or includes
them in argv, environment, webview, MCP or diagnostics. Lock stops access and
restarts the shell to clear its visible state; the durable lock marker also
prevents a subsequent headless start. Encrypted copies start with a fresh local
device identity, private AI settings, and MCP off. The app has no plaintext
export operation for encrypted workspaces.

## Owner acceptance

1. Prepare a Developer ID provisioning profile authorizing the app ID
   `<TEAM_ID>.org.fulcrum.desktop` and its same-name Keychain access group.
   Add its base64 contents as `APPLE_WORKSPACE_PROVISION_PROFILE` in the
   GitHub Actions release environment. Use the normal [P5 procedure](P5.md).
   Keep the signing identity and authorized group consistent for updates.
   See [Apple's data protection Keychain guidance](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains).
2. In signed builds on Intel and Apple Silicon, make a synthetic workspace.
   In Settings → Privacy & Data, choose **Create encrypted copy**. Cancel at
   the folder and recovery prompts once; verify the original remains usable.
   Complete the copy, save the recovery card offline, and re-enter it. Verify
   history, command/undo, fresh device identity, and the retained plaintext
   source and backup. Never include a recovery card in screenshots or reports.
3. Lock, then test startup, MCP, and reopen after first unlock and after reboot.
   Confirm no reads or writes while locked. In the Fulcrum app menu, choose
   **Unlock Encrypted Workspace**. Test denied, missing and wrong credentials.
   Confirm no plaintext fallback. Use Activity Monitor to check the old core
   exits and no recovered secret appears in process arguments.
4. Make an encrypted backup and restore through Backup & Recovery. Rotate the
   key from the app menu. Verify each operation creates a fresh workspace and
   card, preserves the old copy and rejects the old card for the new identity.
5. After S1, use disposable offline-available Dropbox and Drive folders on two
   Macs. Open the verified encrypted copy on the second Mac and import the
   card out of band. Test wrong cards, corrupt/missing files, interrupted copies,
   conflicted copies, cross-device edits, history/undo and no automatic
   credential/source/MCP activation. Record actual pass/fail and gaps here,
   then tick step 36's Owner box. Do not ship encryption on unsigned results.

## Validation boundary

Synthetic tests exercise the native key driver contract through an in-memory
port, an independent libsodium vector, record authentication, recovery,
migration and restore, lock markers, and the existing core command path.
No user workspace, real Keychain item, release profile or signed two-Mac
configuration was used. A development build cannot verify the Keychain ACL.
