# S4 — Slack and Gmail connector capability matrix

Owner direction now requires Activepieces for source integrations
([ADR-0011](../decisions/0011-activepieces-integration-boundary.md)). The native
recommendation below is historical research; the probes remain test instruments.
Piece capability, permission and runtime gaps still require validation.

Research date: 2026-11-07. Status: source review and mocked read-only probes
complete; throwaway-account OAuth, rate behavior and footprint measurements
pending. No account has been connected and no runtime has been installed.

## Recommendation

Provisionally prefer native vendor APIs behind `SourceAdapter`, with the
official SDKs considered during I2. The small probes use Node's HTTP client to
keep this spike independent of the unmerged C1 scaffold. Fulcrum still owns
scope opt-in, bounded backfill, pagination, checkpoints and dedupe. No connector
writes domain state. This recommendation is an inference from the documented
capabilities below, not measured proof of reliability or resource savings.

Activepieces has useful read actions; it is not missing Gmail history or Slack
threads. But importing a piece does not supply its runtime services, connection
management or a durable bounded-pull contract. Default piece auth also includes
write scopes. The self-hosted runtime remains an optional comparison, not a
new Fulcrum dependency. Keep ADR-0002 Provisional until the owner runs the tests
and the decision checkpoint evaluates results.

The Slack commercial unlisted-app limit documented in the
[current changelog](https://docs.slack.dev/changelog/2025/05/29/rate-limit-changes-for-non-marketplace-apps/)
is one history/replies request per minute with at most 15 objects. Internal
apps are treated differently; do not generalize the historical rollout dates.
Gmail's [quota page](https://developers.google.com/workspace/gmail/api/reference/quota)
changed in May 2026; older projects can retain prior quotas. Record the actual
Cloud Console quota values, per-method costs and observed error headers.

Activepieces currently documents a hobbyist single-container PGLite/in-memory
queue setup and a separate recommended Compose/PostgreSQL/Redis setup. Neither
is a measured no-Docker packaged sidecar. Do not install either while S2 is
measuring this Mac. [Hobbyist installation](https://www.activepieces.com/docs/install/options/docker),
[installation options](https://www.activepieces.com/docs/install/overview).

## OAuth and distribution reality

Gmail `gmail.readonly` is a restricted scope. A public release may require
verification; restricted data stored/transmitted through servers can trigger
additional security-assessment requirements. An alpha using the owner's own
project/test account is not evidence of public distribution approval. Testing
mode refresh tokens normally expire after seven days for Gmail scopes. Admin
policy can still deny access. [Scopes](https://developers.google.com/workspace/gmail/api/auth/scopes),
[refresh lifecycle](https://developers.google.com/identity/protocols/oauth2).

The prototype uses env tokens, not an embedded client secret. The eventual
desktop app needs a system-browser flow with PKCE and a loopback redirect;
desktop clients cannot keep a distributed client secret confidential.
[Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app).

Slack alpha: create an internal app in the fake workspace and request only the
read scopes needed for the chosen conversation type. Workspace/admin approval,
user versus bot token access and membership must be tested. A public,
multi-workspace commercial app has different distribution/rate constraints.
Slack rotation, when enabled, uses expiring access tokens and replaces refresh
tokens; a long-lived test token does not validate that lifecycle.
[OAuth](https://docs.slack.dev/authentication/installing-with-oauth/),
[rotation](https://docs.slack.dev/authentication/using-token-rotation/),
[thread API](https://docs.slack.dev/reference/methods/conversations.replies/).

The current Activepieces auth source requests mutation permissions for both
sources. Reusing that definition unchanged would exceed Fulcrum's read-only
ingestion needs. This is a reason to adapt or replace it, not a claim that
Activepieces cannot support narrower custom credentials.

## What was verified

Tests use fake provider responses; they verify fixed read-only routes,
Authorization headers, redirect refusal, sanitized errors, Retry-After,
bounded/resumable pagination, exact Slack timestamp strings, Gmail history
boundaries/expiration, and env-only Google refresh handling. No real service,
account OAuth flow, token refresh, retention window, DM access, permalink
click-through, Activepieces execution or footprint has been validated.

See [the owner procedure](../../spikes/s4/README.md) for exact setup and commands.
