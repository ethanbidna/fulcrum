# S4 — Slack and Gmail connector capability matrix

Owner direction now requires Activepieces for source integrations
([ADR-0011](../decisions/0011-activepieces-integration-boundary.md)). The native
recommendation below is historical research; the probes remain test instruments.
Piece capability, permission and runtime gaps still require validation.

Research began on 2026-11-07. The capability tables below describe the
initial source review. See Owner results for later Gmail and runtime evidence.

## Recommendation

[ADR-0027](../decisions/0027-gmail-piece-execution.md) selects direct execution
of a read-only Activepieces piece for I2. The paragraphs below describe the
initial research recommendation.

Provisionally prefer native vendor APIs behind `SourceAdapter`, with the
official SDKs considered during I2. The small probes use Node's HTTP client to
keep this spike independent of the unmerged C1 scaffold. Fulcrum still owns
scope opt-in, bounded backfill, pagination, checkpoints and dedupe. No connector
writes domain state. This recommendation is an inference from the documented
capabilities below, not measured proof of reliability or resource savings.

Activepieces has useful read actions; it is not missing Gmail history or Slack
threads. But importing a piece does not supply its runtime services, connection
management or a durable bounded-pull contract. Default piece auth also includes
write scopes. The self-hosted runtime remains an optional comparison, not a
new Fulcrum dependency. ADR-0011 superseded ADR-0002 after this initial review.

## OAuth and distribution reality

Gmail `gmail.readonly` is a restricted scope. A public release may require
verification; restricted data stored/transmitted through servers can trigger
additional security-assessment requirements. An alpha using the owner's own
project/test account is not evidence of public distribution approval. Testing
mode refresh tokens normally expire after seven days for Gmail scopes. Admin
policy can still deny access. [Scopes](https://developers.google.com/workspace/gmail/api/auth/scopes),
[refresh lifecycle](https://developers.google.com/identity/protocols/oauth2).

The prototype uses env tokens, not an embedded client secret. The eventual
desktop app needs a system-browser flow with PKCE and a loopback redirect;
desktop clients cannot keep a distributed client secret confidential.
[Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app).

Slack alpha: create an internal app in the fake workspace and request only the
read scopes needed for the chosen conversation type. Workspace/admin approval,
user versus bot token access and membership must be tested. A public,
multi-workspace commercial app has different distribution/rate constraints.
Slack rotation, when enabled, uses expiring access tokens and replaces refresh
tokens; a long-lived test token does not validate that lifecycle.
[OAuth](https://docs.slack.dev/authentication/installing-with-oauth/),
[rotation](https://docs.slack.dev/authentication/using-token-rotation/),
[thread API](https://docs.slack.dev/reference/methods/conversations.replies/).

The current Activepieces auth source requests mutation permissions for both
sources. Reusing that definition unchanged would exceed Fulcrum's read-only
ingestion needs. This is a reason to adapt or replace it, not a claim that
Activepieces cannot support narrower custom credentials.

## Addendum (2026-11-15): "can Activepieces be the engine, and how"

Re-check of the pieces, licenses and Google OAuth constraints against the
owner's rules: no IMAP or app password, no forwarding, no Google
verification or CASA assessment. Package facts come from the npm tarballs
(`@activepieces/piece-gmail@0.19.0`, `piece-slack@0.23.2`) and the upstream
repository; nothing here used a real account.

### Verdict

Yes for both sources, as **option (a): pieces as libraries in the local
core**. Option (b) stays rejected for the desktop product (1.04 GiB idle
container, 2.20 GiB image, Docker, stock Gmail OAuth requests write scopes).
Option (c) remains a fallback for any action a piece cannot express. This is
the route [ADR-0027](../decisions/0027-gmail-piece-execution.md) already
selects for Gmail; Slack has no live evidence yet and stays provisional.

### License check

- Upstream root `LICENSE` is MIT Expat except `packages/ee/` and
  `packages/server/api/src/app/ee`, which carry a commercial license.
- Both pieces live in `packages/pieces/community/<name>/`, outside `ee`, so
  they fall under MIT.
- The published npm packages have **no `license` field and no LICENSE
  file** in the tarball, and ship a single bundled `src/index.js` with
  dependencies (including Google client libraries) folded in. Cite the
  upstream MIT license and the exact source commit in the notice file; do
  not rely on npm metadata. `@activepieces/pieces-framework` and
  `pieces-common` also lack a license field in `npm view`, and need the
  same upstream citation.
- Re-verify the directory per piece on every version bump; the
  enterprise-only features (not pieces) are not needed.

### Runtime requirements

Pieces need no Docker, Postgres or Redis. They are plain Node modules that
take an auth object and a context. The Gmail tarball is 2.46 MB unpacked
(0.18.6), the Slack tarball 1.30 MB; measured Gmail RSS and footprint are in
[gmail-desktop.md](S4-results/gmail-desktop.md). Slack footprint is unmeasured.

### Scopes

- Gmail piece auth requests `gmail.readonly`, `gmail.send`,
  `gmail.compose` and `gmail.modify` (confirmed in the 0.19.0 bundle). Fulcrum
  must supply its own read-only auth, as the extension in
  `spikes/s4/gmail-piece` does.
- `gmail.metadata` is not workable: it returns headers and labels but not
  bodies and does not allow the `q` search parameter, which backfill by
  label and date needs (per Google's scope documentation; not retested).
  The narrowest usable scope is `gmail.readonly`. Per-label limiting is
  Fulcrum's own filtering, not a Google permission boundary.
- Slack piece bundle references many write scopes (`chat:write`,
  `channels:write`, `files:write`, ...). A Fulcrum Slack app would request
  only `channels:history/read`, `groups:history/read`, `im:history/read`,
  `mpim:history/read`, plus `users:read`, and the host would pass the
  resulting token to read-only actions.

### How OAuth client credentials reach a library piece

A piece's `auth` is a declaration (URLs, scopes). The Activepieces server
normally injects the client id and secret and performs the code exchange.
Used as a library, there is no such server: the host performs the browser
flow with PKCE and a loopback redirect, stores the refresh token in
Keychain, refreshes it, and passes a short-lived access token to the action
as `auth`. The client id (and secret, which Google still issues to
desktop clients) is Fulcrum's, supplied at build time or by the user; the
spike used environment variables. A desktop client secret is not
confidential.

### Google OAuth reality for the chosen route

Route: a Fulcrum-owned (or user-owned) Google Cloud OAuth client, left
unverified, scope `gmail.readonly`.

- **Testing mode:** only listed test users (up to 100), and refresh tokens
  expire after 7 days. Unsuitable for daily use.
- **Production, unverified:** the consent screen shows a "Google hasn't
  verified this app" warning the user must click through ("Advanced"). New
  authorizations are capped at 100 users for the life of the project, which
  is a hard ceiling on distribution. Restricted-scope verification and the
  annual security assessment (CASA) are the only way past it, and the owner
  has ruled them out.
- Token expiry and the 100-user count apply per Cloud project, so a
  user-created client (guided setup) avoids the shared cap at the cost of a
  harder install for non-technical users.
- These Google facts are from Google's published OAuth documentation and the
  existing notes above; the cap and warning screen were not exercised here.

### Getting past the 100-user cap without paying

Counts are per Cloud project. Recommended: ship a Fulcrum-owned client for
the first 100 users and a guided "use your own Google project" flow (free,
unverified, published to production so tokens do not expire after 7
days) for everyone else; make the own-project flow the default design.
Workspace "Internal" apps suit single organizations only. Do not create
several Fulcrum projects to multiply the cap (likely against Google's
terms). Verification plus CASA is the only way to lift the cap on a shared
client and is excluded. From Google's documentation; not exercised.
